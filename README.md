# AlgoLab

Локальный тренажёр по алгоритмическим задачам. Задача даётся с условием и
эталонными решениями разной сложности; вместо того чтобы верить заявленной
Big-O на слово, AlgoLab прогоняет решение на входах растущего размера и
подгоняет измеренную кривую под класс сложности — так расхождение между
«написано O(n)» и «на деле O(n^2)» видно, а не декларируется.

## Запуск для пользователя

Нужен только Docker.

```bash
docker compose up
```

Открыть [http://localhost:8080](http://localhost:8080).

Сборка тянет Node-образ для фронтенда и SDK-образ для бэкенда, но в итоговом
образе остаётся только рантайм ASP.NET и опубликованный вывод — ни .NET SDK,
ни Node, ни `node_modules` в контейнере нет.

### Ограничение контейнера

**В контейнере доступен только режим витрины.** Можно посмотреть условия,
прочитать эталонные решения, прогнать их на тестах и снять кривую роста.
Написать и запустить свою попытку — нельзя: попытка (`[Solution(Kind =
SolutionKind.Attempt)]`) — это C#-класс, который компилируется в сборку
`AlgoLab.Problems`, а для этого нужны .NET SDK и IDE, которых в контейнере
осознанно нет. Чтобы решать задачи самому, нужен путь разработки ниже.

## Запуск для разработки

Нужны .NET SDK (версия закреплена в `global.json`) и Node.js для фронтенда.

- Visual Studio 2022: открыть `AlgoLab.sln`, нажать F5 (профиль `AlgoLab.Api`
  поднимает и API, и dev-сервер фронтенда через SPA-прокси);
- либо из терминала:

  ```bash
  dotnet run --project src/AlgoLab.Api
  ```

## Как добавить задачу

Регистрировать задачу нигде не нужно — `ProblemRegistry` находит её
рефлексией по сборке `AlgoLab.Problems`. Достаточно:

1. Создать папку `src/AlgoLab.Problems/<Категория>/<ИмяЗадачи>/` — namespace
   класса задачи должен совпадать с путём папки, например
   `AlgoLab.Problems.HashTable.TwoSum` для
   `src/AlgoLab.Problems/HashTable/TwoSum/`.
2. Описать задачу классом, унаследованным от `Problem<TInput, TOutput>`:
   условие (`Info`), тест-кейсы (`Cases`) и, если нужна кривая роста —
   генератор входа (`Scaler`).
3. Добавить одно или несколько решений — классы `ISolution<TInput, TOutput>`
   с атрибутом `[Solution("Название", Time = Complexity.ON, Space =
   Complexity.O1)]`, где `Time`/`Space` — заявленная сложность. Один из
   классов может быть нерабочей попыткой (`Kind = SolutionKind.Attempt`,
   `throw new NotImplementedException()`).
4. Написать `README.md` рядом — своими словами, со ссылкой на оригинал (см.
   ниже).

Тип входа и выхода в `Problem<,>` и в `ISolution<,>` должны совпадать — по
этой паре типов решения привязываются к задаче автоматически.

## Как читать вердикт по сложности

Для задач с генератором входа AlgoLab запускает решение на растущих `n`,
измеряет время и аллокации кучи и подбирает для каждого класса сложности
кривую `y = a · f(n)` методом наименьших квадратов. У заявленного и у лучшего
подобранного класса есть текстовое представление (`O(n)`, `O(n log n)` и
т. д.) и один из трёх вердиктов:

- **согласуется** — измерения не противоречат заявленному классу;
- **расходится** — измерения заметно ближе к другому классу;
- **данных мало** — точек недостаточно или подгонка нигде не дотягивает до
  порога качества.

Важная оговорка: **на достижимых в разумное время `n` соседние классы (в
первую очередь `O(n)` и `O(n log n)`) почти неразличимы** — их кривые роста
слишком похожи, чтобы полином, гоняющий алгоритм до `n` в десятки тысяч,
надёжно развёл их по качеству подгонки. Поэтому вердикт — это «согласуется
или расходится с тем, что заявлено», а не независимое доказательство точного
класса сложности. Он ловит грубые ошибки (заявлен `O(n)`, а на деле
`O(n^2)`), но не заменяет разбор алгоритма.
