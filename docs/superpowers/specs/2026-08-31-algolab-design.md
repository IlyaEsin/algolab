# AlgoLab — дизайн

Дата: 2026-08-31
Статус: утверждён, готов к написанию плана реализации

## 1. Зачем

Личный тренажёр для подготовки к алгоритмическим интервью. Копилка решённых задач с LeetCode и подобных сайтов, где по каждой задаче видно условие, эталонные решения, разбор идеи и сложность в Big-O — как заявленную, так и измеренную на реальных запусках.

Основной сценарий: **сначала решить самому**. Пользователь открывает задачу, видит условие, пишет свою попытку в Visual Studio, запускает её из веб-UI по тест-кейсам и только потом раскрывает эталон. Эталонные решения по умолчанию скрыты.

Проект публикуется на GitHub публично и должен запускаться у постороннего человека одной командой `docker compose up`.

## 2. Ограничения окружения

| Ограничение | Следствие |
| --- | --- |
| Visual Studio 2022 + ReSharper | Таргет `net9.0`. VS 2022 не открывает проекты на .NET 10 — для него нужна VS 2026. `global.json` пинит SDK 9.0.317, иначе консольный `dotnet build` возьмёт установленный SDK 10 и разойдётся со студией. |
| Windows, путь `C:\code\algolab` | Короткий корень — меньше риска упереться в лимит длины пути Windows при вложенных папках задач и `node_modules`. |
| Публичный репозиторий | Условия задач формулируются своими словами со ссылкой на оригинал. Тексты LeetCode защищены копирайтом и в репозиторий не копируются. Лицензия MIT. |
| Docker-запуск у третьих лиц | Исходники задач вкладываются в сборку как embedded resources, а не читаются с диска по пути к репозиторию. |

## 4. Модель задачи

Три сущности: задача, решение, реестр.

```csharp
public interface ISolution<TInput, TOutput>
{
    TOutput Solve(TInput input);
}

public abstract class Problem<TInput, TOutput>
{
    public abstract ProblemInfo Info { get; }
    public abstract IEnumerable<TestCase<TInput, TOutput>> Cases { get; }

    public virtual IOutputComparer<TOutput> Comparer => StructuralComparer<TOutput>.Instance;
    public virtual IInputScaler<TInput>? Scaler => null;
}
```

`ProblemInfo` несёт slug, заголовок, ссылку на источник, сложность и теги.

Вход каждой задачи — свой `record`. Он же служит ключом привязки: реестр сопоставляет решение с задачей по паре generic-аргументов `(TInput, TOutput)`. Прицепить решение не к той задаче невозможно — типы не сойдутся. Строковых ссылок между решением и задачей нет, рассинхрон исключён по построению.

Решения помечаются атрибутом:

```csharp
[Solution("Хеш-таблица", Time = Complexity.ON, Space = Complexity.ON)]
public sealed class TwoSumHashMap : ISolution<TwoSumInput, int[]>;

[Solution("Перебор пар", Time = Complexity.ON2, Space = Complexity.O1)]
public sealed class TwoSumBruteForce : ISolution<TwoSumInput, int[]>;

[Solution("Моя попытка", Kind = SolutionKind.Attempt)]
public sealed class TwoSumAttempt : ISolution<TwoSumInput, int[]>;
```

Ключевые решения модели:

- **Сложность — enum `Complexity`** (`O1`, `OLogN`, `ON`, `ONLogN`, `ON2`, `ON3`, `O2N`, `ONFactorial`), а не строка. Строку невозможно сопоставить с измеренной кривой; enum несёт функцию роста, по которой строится вердикт.
- **Сравнение ответов настраивается.** По умолчанию структурное равенство с поддержкой массивов и вложенных коллекций. Задачи с несколькими верными ответами (перестановки, любая подходящая пара индексов, float с погрешностью) переопределяют `Comparer`. Без этого такие задачи пришлось бы искусственно подгонять под единственный ответ.
- **Попытка — обычный класс в репозитории**, коммитится. Пишется в студии с полным IntelliSense и ReSharper. Пока внутри `NotImplementedException`, раннер показывает статус «не реализовано», а не ошибку.
- **Design-задачи** (LRU Cache, Min Stack) укладываются в ту же модель: входом становится список операций, выходом — список результатов. Проверяется на стартовом наборе.

Раскладка папки задачи:

```
src/AlgoLab.Problems/HashTable/TwoSum/
  TwoSum.cs               record входа + класс задачи (Info, Cases, Scaler)
  TwoSumBruteForce.cs
  TwoSumHashMap.cs
  TwoSumAttempt.cs
  README.md               условие своими словами + разбор идеи отдельным разделом
```

`README.md` и `.cs` вкладываются в сборку как embedded resources и отдаются в UI. Разбор идеи лежит отдельным разделом, чтобы условие читалось без спойлера.

## 5. Исполнение

**Изоляция процессом.** API не исполняет код задач у себя. Он запускает `AlgoLab.Runner` как дочерний процесс и читает JSON из stdout.

Причина: попытка с бесконечным циклом. В .NET поток нельзя прервать снаружи (`Thread.Abort` отсутствует в Core), а запуск в `Task` с таймаутом оставляет навсегда крутящий CPU поток. Один зациклившийся `while` деградировал бы веб-сервер до ручного перезапуска. Дочерний процесс убивается по таймауту без последствий. Побочная выгода — чистые замеры в свежем процессе без GC-шума и разогретых пулов ASP.NET. Цена — около 120 мс на старт процесса, незаметно на фоне сетевого запроса из браузера.

**Прогон тест-кейсов.** По каждому кейсу возвращаются вход, ожидание, факт, время и вердикт. `NotImplementedException` трактуется как статус «не реализовано». Бюджет процесса по умолчанию 5 секунд, задача может его поднять.

**Кривая роста.** Использует `Scaler`: по числу N он строит вход нужного размера с фиксированным seed, поэтому замер воспроизводим.

Лестница N адаптивная — старт с малого значения, удвоение, остановка по достижению потолка или по исчерпанию бюджета (~2 с на решение). Без бюджета решение с `O(2^n)` подвесило бы запрос, а именно такие интересно смотреть рядом с оптимальным.

На каждом N выполняется разогрев (иначе первые замеры меряют JIT), затем несколько повторов, из которых берётся **медиана** — одна пауза GC перекашивает среднее втрое. Параллельно снимается `GC.GetAllocatedBytesForCurrentThread`, что даёт вторую кривую, по памяти, и позволяет проверять заявленный `Space` так же, как `Time`.

**Вердикт по Big-O.** Измеренные точки подгоняются под каждую модель-кандидата из `Complexity`; лучшая по качеству подгонки показывается рядом с заявленной.

Ограничение фиксируется в UI явно: отличить `O(n)` от `O(n log n)` эмпирически на достижимых N нельзя — логарифм там почти константа. Поэтому вердикт формулируется как «согласуется с заявленным» либо «расходится», а не как доказательство. Расхождение на порядок (заявлено `O(n)`, ложится на `n^2`) детектируется надёжно — ради этого механизм и существует.

## 6. API

Без состояния, без базы данных.

```
GET  /api/problems            список: slug, заголовок, сложность, теги, измерима ли задача
GET  /api/problems/{slug}     условие, разбор, кейсы, решения с исходниками и Big-O
POST /api/run                 { slug, solution } → результаты по кейсам
POST /api/measure             { slug, solutions[] } → кривые времени и памяти + вердикты
```

`measure` принимает несколько решений за раз, чтобы наложить кривые перебора и оптимального решения на один график — это основной визуальный результат проекта.

Каталог задач не исполняет код решений: всякое исполнение идёт через дочерний процесс. Поэтому отметка «задача решена» вычисляется не сервером, а браузером после успешного прогона попытки, и хранится в localStorage рядом с состоянием раскрытия эталонов. Иначе список задач исполнял бы все попытки на каждый запрос, и одна зациклившаяся вешала бы весь экран.

## 7. Фронт

React 19 + TypeScript на Vite. Tailwind для вёрстки, Recharts для графиков, Shiki для подсветки C# (настоящая TextMate-грамматика, а не регулярки), react-markdown для условий.

Экран: слева список задач с фильтром по тегам, сложности и статусу попытки; справа выбранная задача. По умолчанию открыто условие — эталонные решения свёрнуты за действием «Показать решение», состояние раскрытия хранится в localStorage, чтобы перезагрузка страницы не спойлерила задачу повторно.

Вкладка замеров: график в лог-лог осях, линия на решение, бейдж вида «заявлено `O(n^2)` · измерено `n^2` ✓».

## 8. Тесты

`AlgoLab.Tests` на xUnit не содержит рукописных тестов на конкретные задачи. Он обходит реестр и порождает теории: каждое эталонное решение × каждый тест-кейс. Добавленная задача покрывается автоматически.

Сторожевые тесты целостности реестра:

- у задачи есть `README.md`;
- у задачи есть хотя бы одно эталонное решение;
- slug уникален и совпадает с именем папки;
- `Scaler`, если он есть, выдаёт вход, на котором эталон отрабатывает.

Попытки в CI не гоняются: нерешённая задача не должна ронять сборку.

## 9. Docker

Трёхстадийная сборка: `node:22-alpine` собирает фронт в статику → `dotnet/sdk:9.0` кладёт статику в `wwwroot` и публикует API вместе с Runner → `dotnet/aspnet:9.0` запускает. В финальном образе нет ни SDK, ни Node.

`docker compose up` поднимает приложение на `http://localhost:8080` без установленных .NET и Node.

В контейнере проект работает в режиме витрины: условия, эталоны, разбор, прогон тестов и кривые роста. Написание своей попытки требует пересборки, то есть SDK и IDE, и в контейнере не поддерживается. Это указывается в README явно.

## 10. CI

GitHub Actions на push: restore, build, test, сборка фронта и сборка Docker-образа. Образ собирается в CI намеренно — иначе Dockerfile тихо протухнет и «склонировал и запустил» перестанет работать ровно тогда, когда понадобится.

## 11. Claude-инфраструктура

- `CLAUDE.md` — таргет `net9.0` и причина (VS 2022), карта репозитория, правило о собственных формулировках условий, стиль.
- `.claude/settings.json` — permissions на `dotnet`, `npm`, `git`, `gh`.
- Скилл **build-test** — `dotnet build`, `dotnet test` и сборка фронта одной командой.
- Скилл **add-problem** — создаёт папку задачи по шаблону со всеми файлами и заполненными метаданными, оставляя Attempt пустым. Регистрация нигде не нужна, задачу найдёт рефлексия.
- `codebase-memory-mcp` подключается к проекту.

RTK-хук, superpowers и плагины живут в глобальных настройках пользователя и работают в новом репозитории без переноса.

## 12. Стартовый набор задач

Восемь задач, подобранных не по популярности, а чтобы продавить модель по всем формам входа: массив, строка, связный список, дерево, граф на сетке, DP, куча и одна design-задача (LRU Cache). Если модель где-то треснет, это выяснится на восьми задачах, а не на восьмидесяти.

## 13. Вне скоупа

Сознательно не делается в первой версии:

- редактирование кода в браузере и компиляция через Roslyn — попытка пишется в IDE;
- база данных, авторизация, аккаунты;
- отслеживание прогресса и интервальные повторения;
- BenchmarkDotNet — точнее, но десятки секунд на запуск, что несовместимо с интерактивным UI;
- деплой куда-либо, кроме локального запуска и Docker.

## 14. Риски

| Риск | Смягчение |
| --- | --- |
| Эмпирическая кривая не различает близкие классы сложности | Вердикт формулируется как согласие/расхождение, ограничение написано в UI |
| Design-задачи не лягут в `Solve(input)` | Проверяется на LRU Cache в стартовом наборе, до того как задач станет много |
| Замеры на ноутбуке шумят (турбо, фоновые процессы) | Отдельный процесс, разогрев, медиана, фиксированный seed |
| Правка попытки требует пересборки | `dotnet watch` в консоли и Hot Reload в студии для правок тела метода |
